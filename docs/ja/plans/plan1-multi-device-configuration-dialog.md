# plan1 マルチデバイス構成ダイアログと一括適用

2026-10-24の検討内容を保存する。調査基準は`develop`の`a67b55c`。本書は実装前の計画であり、計画の保存時点ではコードや稼働中の設定を変更していない。

## 背景と目的

現在の設定画面は、編集内容をすぐに再生へ反映する。親画面のApplyで永続化し、Cancelでは画面を開いた時点、または最後のApply時点へ戻す。以下では、保存前の設定を再生へ反映する操作をライブ反映と呼ぶ。

マルチモードのデバイス構成にも同じ方式を使っている。このため、デバイスの有効化やチャンネル割り当てを少し変更するたびに出力経路が再構成される。利用者から、編集中の再生音声に断続的なノイズが入るとの報告がある。構成画面も扱いにくく、音声処理側のノイズ調査に先行して整理することになった。

出力構成を専用のモーダルダイアログで編集する。モーダルとは、開いている間は親画面を操作できないダイアログを指す。編集中は現在の再生経路を維持し、利用者の確定操作で完成した構成だけを一括適用する。

適用そのものに伴う瞬断、クリック音、持続するノイズの原因調査と修正は後続の課題とする。本計画では、編集操作に伴う不要な再構成をなくす。確定時に無音やノイズが全く生じないことまでは完了条件に含めない。

## 出力プロファイルとの関係

出力プロファイルは、OSが音声機器をどの出力方式とチャンネル構成で扱うかを表す設定である。EffeTuneの音質調整プリセットとは別に管理する。

今回の調査では、2台目のDACに対してPipeTuneが`analog-stereo`を保存していた。一方、再接続後のOSは`iec958-stereo`を有効にしていた。PipeTuneは同じデバイスでもプロファイルが異なると接続を保留するため、ch3/4への経路が作られなかった。

現行のOutput画面にはプロファイルの切り替え機能がない。「デバイスを再割り当て…」は、OSが現在公開している出力へ保存済みの対応を更新する操作である。OS側のプロファイルは変更しない。マルチモードではUbuntu側の物理出力を選択肢から隠すため、PipeTuneの画面だけで元のプロファイルへ戻せない。

新しいダイアログにはプロファイル選択も含める。選択肢を変えただけではOSへ反映せず、他の構成変更とともに確定時に適用する。利用可能なプロファイルの列挙とOS側の切り替えは、現在の出力一覧取得に加えて実装が必要となる。

## 画面構成

親のOutputページには、出力モード、現在の構成の要約、接続状態と「デバイス構成…」ボタンを置く。デバイスごとの詳細編集は専用ダイアログへ移す。親画面の要約は、反映済みの構成と未保存であることを判断できる表示にする。

ダイアログでは、使用するデバイスとプロファイルを選ぶ。各デバイスの物理チャンネルに対して、EffeTuneの最終出力番号と用途名を編集できるようにする。無効化したデバイスや未接続デバイスの予約チャンネルも同じ画面で確認する。

構成全体を見ながら編集できる配置とし、個々の変更で確認ダイアログを重ねない。変更内容は最後の確定操作でまとめて反映する。親画面のApplyと役割が違うため、子ダイアログの確定ボタンは「構成を反映」とする。

接続状態や経路の稼働状態は編集中も更新する。ただし、デバイス一覧の更新を理由に編集内容を上書きしない。現在の稼働状態と、反映前の構成を混同しない表示にする。

## 反映・保存・キャンセル

保存方式は提案の基本案を採用する。子ダイアログで一括ライブ反映し、親画面のApplyで永続化する。子の確定を独立した永続化操作にはせず、親画面全体のApplyとCancelの意味を維持する。

| 操作 | 再生中の構成 | 永続化 |
| --- | --- | --- |
| 子ダイアログを開く | 変更しない | しない |
| デバイス、プロファイル、割り当て、用途名を編集する | 変更しない | しない |
| 子のCancel、Esc、ウインドウを閉じる | 編集を破棄する。子を開く直前の構成を維持する | しない |
| 子の「構成を反映」 | 完成した構成を一括適用する | しない |
| 変更のない構成を確定する | 変更要求を送らない | しない |
| 親のApply | 出力を再適用しない | 反映済みの設定を保存する |
| 親のCancel | 親を開いた時点、または最後のApply時点へ一括復元する | 変更しない |

子ダイアログの編集内容は、親のライブ反映対象から分離して保持する。デバイスのチェックやチャンネル番号の変更では、親の設定更新処理を呼ばない。確定時だけ、完成した出力構成を親の設定処理へ渡す。

確定後は、デーモンが適用結果を返すまで重複した要求を送らない。成功を確認してからダイアログを閉じ、親画面へ反映済みの構成を表示する。失敗時はダイアログを残し、編集内容とエラーを表示する。失敗した構成を反映済みとして扱わない。

子で確定した後に親をCancelした場合は、出力構成も復元対象となる。プロファイルを変更した場合はOS側も復元対象に含める。親のApplyが成功すれば、その状態を次のCancelで戻す基準にする。保存に失敗した場合は基準を更新せず、既存の保存失敗表示と再試行の扱いを維持する。

## モードとプリセットの整合

初めてマルチモードへ移る場合は、デバイス構成の確定とモード変更をまとめる。不完全な構成を先に適用してからデバイスを追加する流れにはしない。構成を取り消した場合は、元の再生モードを維持する。

出力幅は、予約分を含む保存済みのチャンネル構成から決まる。既存の上限である16チャンネルを維持し、接続状態の変化や無効化で番号を自動的に繰り上げない。

確定時には、新しい出力幅で現在のプリセットを処理できることを確認する。不適合ならエラーを表示し、現在の構成を維持する。プリセットを暗黙に変更したり、Bypassへ切り替えたりしない。

不適合な場合は、子をCancelして親画面へ戻る。現在と変更後の幅を扱えるプリセット、またはBypassを利用者が明示的に選び、構成変更をやり直す。構成を反映した後、親画面で目的のプリセットを選択できる。この手順をエラーから案内し、親画面を操作できないまま変更が行き詰まらないようにする。

出力構成とプリセットの両方を変更する必要がある場合は、既存の同時適用処理を利用する。親画面のCancelでも、出力幅とプリセットを一つの要求で復元する。レートやDSPバックエンドの変更が進行中の場合は、既存の設定処理の依存順序に従う。

## プロファイル変更と再構成

プロファイルの選択も子ダイアログ内の編集値として扱う。確定時に、選択したプロファイルとチャンネル構成を検証してOSへ適用する。入力も備える機器では、出力の変更によって入力側の設定を変えないようにする。

プロファイル変更に伴うデバイスの再列挙を、個別の出力変更として逐次適用しない。デーモン側で一つの構成変更として管理し、必要な出力が揃ってから最終的な配信経路を構成する。

ここでいう一括適用は、利用者が確定した一つの構成を一つの操作として扱うことを意味する。複数機器のOS設定変更や通知が、物理的に同時となることを前提にはしない。途中の失敗では旧プロファイルと旧構成への復元を行い、復元できなかった場合は実際の状態と失敗内容を表示する。

保存したプロファイルは再接続時にも復元する。子でのライブ反映、親Applyによる保存、親Cancelによる復元を通して、PipeTuneの保存内容とOS側の設定が食い違わないようにする。

## 外部変更とデバイスの喪失

確定前に、最新の接続状態と設定の変更番号を確認する。変更番号とは、デーモンが設定変更ごとに更新する値である。他のクライアントによる設定変更を、古い編集内容で上書きしないために使う。

デバイスの切断やプロファイルの変化は、設定の変更番号だけでは検出できない。最新の出力一覧も照合し、編集中に選択先が変わった場合はその内容を表示する。編集内容は保持し、不一致を成功として扱わない。

既存の未接続デバイスに対するチャンネル予約は維持する。編集中の構成を、デバイスの抜き差しや通信の再接続だけで自動適用しない。この条件は、機器の切断自体による経路変化を禁止するものではない。

## 実装の進め方

各段階でアプリケーションをビルドし、その段階の機能を操作・検証できるようにする。挙動を確認するテストを先に追加し、REDを確認してから実装してGREENを確認する。段階ごとに適切な粒度でコミットする。

### 1 モーダル編集と一括ライブ反映を導入する

プロファイルを変更しない既存の出力構成を対象に、専用ダイアログと独立した編集状態を導入する。親画面には要約と起動ボタンを配置する。デバイス選択、番号の変更、用途名、予約チャンネルを編集できるようにし、確定時だけ既存の一括適用処理へ渡す。

完了条件は、複数箇所を編集しても確定前の出力変更要求が0件であること。子のキャンセルで再生経路と保存内容が変わらず、確定時には最終構成だけを送ることも確認する。親Applyで再構築せず、親Cancelで出力とプリセットをまとめて復元できることを含める。

コミット例は`feat: batch multi-device edits in a configuration dialog`。

### 2 プロファイル選択と復元を統合する

利用可能なプロファイルを取得し、子ダイアログで選べるようにする。OS側の切り替えと、再列挙後の出力構成の適用を一つの構成変更として管理する。親ApplyとCancel、再接続時の復元にも統合する。

利用する外部APIは、公式文書とAPIコメントの両方で使い方を確認する。内部用APIは使用せず、外部コードも変更しない。新しい依存先の制約を本計画へ追記する場合は、根拠となるURLを併記する。

完了条件は、プロファイルを選び直しても確定前にはOSを変更しないこと。確定した構成が実際の出力へ反映され、親Cancelと再接続で所定の構成へ復元されることを確認する。入力を備える機器では、入力側の設定を維持できることも検証する。

コミット例は`feat: apply output profiles with device configurations`。

### 3 失敗・競合・モード変更を検証して完成させる

初回のマルチモード移行、出力幅とプリセットの不適合、適用途中の失敗、外部設定変更、デバイスの切断と復帰を検証する。確定を繰り返しても要求が重複せず、変更のない構成では要求を送らないことも確認する。

確定済みの挙動をテストへ追加し、必要な修正だけを行う。旧UIの置き換えで不要になった処理を整理し、既存コメントは内容に応じて更新する。機能削除に該当する変更は、プロジェクトの削除確認テストとコミットの手順に従う。

完了条件は、次節の検証項目を満たすこと。最後のコード変更後に全体テストを実行し、ビルド警告も分析して対処する。利用者向け文書は日本語を原本として更新し、他言語へ反映する。一般文書から本計画へのリンクは追加しない。

コミットは内容に応じて`fix:`、`refactor:`、`chore:`、`doc:`へ分ける。

## 検証と最終完了条件

| 検証対象 | 完了条件 |
| --- | --- |
| 編集中の構成変更 | 複数回のデバイス選択、プロファイル選択、割り当て変更を行っても、出力変更要求とOSプロファイル変更は0件 |
| 子ダイアログの破棄 | Cancel、Esc、閉じるのいずれでも、再生中の構成と保存内容が変わらない |
| 一括適用 | 最終構成だけを一つの要求で送り、チャンネルごとの実PCM出力がその構成と一致する |
| 重複と無変更 | 適用中の重複要求がなく、変更のない確定でも要求を送らない |
| 親画面との整合 | Applyは保存だけを行う。Cancelは親の復元基準へ、プロファイルと必要なプリセットを含めて戻す |
| プリセットと出力幅 | 不適合な構成を適用せず、旧構成を維持する。必要な同時変更は一括処理する |
| 接続状態と編集値 | 状態表示を更新しても編集値を失わず、切断や再接続だけで編集内容を適用しない |
| 失敗と外部変更 | 編集値と診断を残し、古い設定で外部変更を上書きしない。復元に失敗した場合も成功表示にしない |
| プロファイルの保存と復元 | 保存後の再接続で構成を復元し、入力を備える機器の入力設定を維持する |
| 全体回帰 | 最終コードで全体テストが成功し、未確認事項と実機での検証範囲を明記する |

既存の[設定モデルテスト](../../../pipetune-gtk/test/dialog-model-test.cpp)、[制御クライアントテスト](../../../pipetune-gtk/test/control-client-test.cpp)、[GTK E2E](../../../pipetune-gtk/test/e2e/tests/dialog.test.ts)を拡張する。一括要求と実出力の対応は、[製品出力テスト](../../../pipetune/test/product_output_test.cpp)と隔離したPipeWire環境で検証する。ソース中の記述や表示文字列の有無だけで完了としない。

タイミングに依存する固定待機を避け、要求の完了、接続状態、受信した音声フレームを基準に判定する。仮想機器だけでは確認できないプロファイルの挙動は実機検証として区別する。計画と実装の前提に矛盾が見つかった場合は、計画を見直してから修正を続ける。
